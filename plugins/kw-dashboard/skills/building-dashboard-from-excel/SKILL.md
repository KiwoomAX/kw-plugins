# building-dashboard-from-excel

업무 엑셀 하나를 DB 표와 계산 코드로 옮긴다. 엑셀 분석기(`explaining-excel-cell`)의 스크립트로 사실 자료를 만들고, 표 정의는 Claude 가 쓴다.

새 구조 전체를 먼저 임시로 실행해 최종 결과표를 엑셀로 검토받고, 엑셀 담당자가 「맞다」고 한 뒤에만 샌드박스에 쌓는다. 화면은 만들지 않는다. 업무용 모니터링 화면은 이 스킬의 범위 밖이고, 다른 개발자가 결과표를 표 이름과 열 이름으로 불러와 만든다. 그래서 표 이름과 열 이름은 바꾸기 어려운 약속이다.

## 묻는 원칙

스스로 알 수 없거나 판단이 애매한 정보는 짐작으로 채우지 않고 모두 스킬을 실행하는 사람에게 묻는다. 결과를 확인할 환경, 표를 둘 스키마가 여기에 든다. 질문은 선택지 창이 아니라 본문으로 한 번에 한 건씩 묻는다.

샌드박스에 쌓기 전에 아래를 알린다.

- 대시보드 화면 서버는 화면을 쓰는 사람의 로그인 토큰으로 샌드박스를 읽고 쓴다. 요청은 그 사람의 권한으로 판정되고, 샌드박스 작업 기록에도 그 사람으로 남는다. 그 사람의 본부가 표를 둔 스키마를 쓸 수 없으면 샌드박스가 거절한다.
- 로그인 토큰은 Kiwoom-Gateway 가 그 화면의 `/api/` 요청에 `X-Auth-Access-Token` 헤더로 넘긴다. 처음에는 빈 값으로 넘기므로, 그 화면에 토큰을 넘기는 설정을 AX팀에 요청한다. 토큰이 비어 오면 화면 서버는 샌드박스를 호출하지 않고 그 사실을 알린다.
- 업로드의 WINUS · WFS 조회와 「WINUS 다시 받기」는 아직 서버 환경 변수 `KIWOOM_ACCESS_KEY` 의 접근 키로 호출한다. 이 키의 주인이 키를 재발급하거나 다른 본부로 옮기거나 퇴사하면 조회가 멈춘다.

## 작업 폴더

엑셀 옆에 `dashboard-work` 폴더를 만들고 아래 파일을 둔다.

| 파일 | 내용 |
|---|---|
| `source_notes.md` | 0단계에서 받은 업데이트 과정 설명(출처 설명) |
| `explain_candidates.json` · `explain_results.json` | 분석기 1번째 실행의 후보 파일과, Claude 가 쓴 결과 파일(표 정의 포함) |
| `explain_facts.json` | 분석기 사실 자료(결과에 쓰이는 셀, 연결 목록, WINUS 추출본 후보, 확인 필요한 사항) |
| `sources.json` | 4단계에서 정한 표별 출처 `{표 id: winus · wfs · manual}` |
| `query_requests.md` | AX 팀에 넘길 쿼리 등록 요청 |
| `table_plan.json` | 만들 표의 설계 |
| `calc.py` | 결과표와 통계 표를 계산하는 코드 |
| `review/` | 새 구조 임시 실행의 저장소(`store/`), 검토 엑셀, 승인본(`approved/`) |
| `sandbox_load/` | 샌드박스 적재 요청 파일과 적재 뒤 대조용 조회 요청(`select/`) |
| `HANDOFF-<엑셀 영문 이름>.md` | 쿼리 등록을 기다릴 때만 남기는 인계 문서 |

## 절차

### 0. 업데이트 과정 듣기

데이터 연결 · 매크로로 들어오는 데이터는 분석기가 찾는다. 화면에서 내려받아 붙여 넣은 값과 펀드 · 종목이 바뀔 때의 처리는 엑셀만 봐서는 알 수 없으므로 그것을 듣는다. 엑셀과 함께 아래 문구로 설명을 받아 `source_notes.md` 에 적는다.

> 작업할 엑셀의 실제 업데이트 프로세스를 설명해 주시면 분석에 도움이 됩니다. 아래는 예시이므로, 참고하셔서 필요한 전달사항이 있는 경우 알려 주세요.
>
> - 자동 연동(SQL · 데이터 연결) 말고, WINUS 나 WFS(우리펀드서비스)에서 엑셀로 내려받아 직접 붙여 넣는 사내 데이터가 있다면 붙이는 시트와 위치, 화면 번호 · 탭, 그 화면에서 넣는 조회 조건
> - 손으로 입력하는 값의 위치, 업데이트할 때마다 새로 넣는지 한 번 넣고 계속 쓰는지, 입력할 때 주의하는 점
> - 펀드나 종목이 새로 생기거나, 빠지거나, 바뀔 때 어떻게 알아채고 어떻게 고치는지(예: 소계 값이 0이 아니면 신규 펀드를 찾아, 그 펀드의 입력값을 검색해 모은 뒤 채움)
> - 그 밖에 업데이트 때마다 직접 손보는 예외(예: 특정 펀드만 값을 직접 덮어씀)
>
> 작업을 시작할까요?

### 1~3. 엑셀 분석과 표 정의 확인

분석기를 슬래시 명령으로 안내하지 않고, 분석기 스크립트를 직접 실행한다. 설명 화면은 만들지 않는다.

1. 분석기 전체 모드의 1번째 실행으로 후보 파일을 만들고, 분석기 `SKILL.md` 전체 모드 2~5번과 같은 문장으로 결과표 · 날짜 시트 군 · 행 순서 · 설정(기준일 입력칸 · 데이터 갱신 단위 · 오늘을 기준일로 받을지)을 묻는다. 결과표는 시트가 아니라 시트 안의 표로 고른다. 답은 분석기 `SKILL.md` 전체 모드 6번대로 `explain_results.json` 에 쓴다.
2. 2번째 실행에 `--facts` 를 붙여 사실 자료 `explain_facts.json` 을 만든다. 결과 파일은 바뀌지 않는다.
3. Claude 가 사실 자료와 엑셀을 보고 결과 파일에 `definitions`(표 범위 · 머리글 · 소계 행 · 역할 · 표 밖 셀), `base_date`(기준일 셀), `parameters`(매개변수 셀)를 쓰고, 사실 자료의 `date_groups` 를 결과 파일로 그대로 옮긴다. 묶음마다 `dates`(`{시트 이름: "YYYY-MM-DD"}`)를 추가해 시트마다 날짜를 적는다. 시트 이름의 모양은 정해져 있지 않으므로 이름을 보고 Claude 가 날짜를 판단하고, 이름만으로 알 수 없는 시트는 개발자에게 묻는다. 9단계 초기 적재는 이 날짜로 지난 날짜 시트를 넣는다. 소계 행은 행 번호와 계산 식 없이 이름 글자와 열로 적는다(`{"label": "소계", "label_col": 이름 글자 열, "group_by": 묶는 열 또는 null, "target": 통계 표 대상, "values": [값 열]}`). 운영 중 행 수가 바뀌고, 소계 계산은 7단계에서 `calc.py` 로 옮기기 때문이다.
4. `table_plan.py check` 로 결과 파일을 검사한다. `missing`(빠진 항목)은 Claude 가 고친다. `uncovered`(결과에 쓰이는데 어느 표 정의 범위에도, 표 밖 셀에도 들지 않는 셀)와 사실 자료의 `unfollowed`(INDIRECT · OFFSET, 깨진 참조, 지난 날짜 시트처럼 따라가지 못한 참조)는 시트와 셀을 보이고 묻는다. 범위가 좁게 잡히면 7단계 대조가 정의 범위 안의 셀만 보므로 드러나지 않기 때문이다. `unlisted`(정의에 적지 않은 소계 · 합계 모양의 행)는 소계로 정의할지 데이터 행으로 둘지 묻는다. 데이터 행으로 두기로 한 행은 그 표 정의의 `data_labels` 에 행 이름 글자를 적는다. 다시 실행해 세 목록이 모두 빌 때까지 한다.

표 정의는 대화로 확인한다. 표마다 한 줄로 시트, 범위, 머리글 행, 소계 · 합계 행 수, 역할을 보이고 한 번에 확인받는다. 개발자는 엑셀을 열어 범위를 확인한다. 사실 자료의 `checks`(확인 필요한 사항)와 Claude 가 정하지 못한 항목(기준일 셀, 모르는 매개변수, 표 밖 셀의 처리)은 0단계 설명과 대조하고, 설명으로 풀리지 않는 항목만 한 건씩 묻는다. 확인한 정의는 `confirmed` 를 `true` 로 바꾸고, 확인되지 않은 정의가 있으면 다음 단계로 가지 않는다. 범위가 애매한 표는 개발자가 원할 때만 분석기 화면으로 본다.

### 4. 원천 출처 확정

0단계 설명과 사실 자료의 `connections`(엑셀 안 쿼리 · 매크로 연결) · `winus_candidates`(붙여 넣은 WINUS 시트 후보)로 표마다 출처를 정해 `sources.json` 에 적는다. 설명과 사실 자료가 다른 표만 묻는다.

- WINUS 에서 오는 표는 `winus`, WFS 에서 오는 표는 `wfs` 다. 둘 다 등록 쿼리로 받는 원천 표다. WINUS 추출본 후보는 0단계 설명에 없어도 화면 번호와 탭을 미리 채워 묻는다. 담당자가 말하지 않은 붙여 넣기 시트가 수기 입력 표로 굳지 않게 하기 위해서다.
- 그 밖의 값은 펀드닥터 같은 외부 서비스나 다른 파일에서 오더라도 `manual`(수기 입력 표)이고, 담당자가 입력 양식에 채워 올린다.
- 다른 파일 링크 중 같은 엑셀의 지난 날짜 파일을 가리키는 칸은 수기 입력으로 일괄 두지 않고, 개발자에게 일반화 · 고정값 · 이전 결과 참조 중에서 고르게 한다. 이전 결과 참조를 고르면 저장된 지난 기준일 결과를 계산 코드가 읽으므로 담당자가 다시 넣지 않아도 된다.
- 원천 표에 화면 번호 · 탭이나 조회 조건이 빠졌으면 그것도 묻는다. 5단계에서 쿼리를 찾을 때 필요하다.

수기 입력 표가 없는 엑셀은 이 스킬의 대상이 아니다. 저장해 둘 사람 입력이 없기 때문이다. 5단계까지만 진행하고, 저장 구조 없이 등록 쿼리로 응용화면을 바로 만들라고 안내한 뒤 끝낸다.

### 5. 쿼리 구하기와 등록 요청

WINUS · WFS 원천 표마다 `searching-winus` 스킬로 등록 쿼리를 찾는다. 화면 번호만으로 고르지 않고 설명의 탭까지 맞춘다. 찾은 쿼리는 번호를 적어 두고, 인자마다 값을 고정 글자나 `{base_date}` · `{yyyymmdd}` 로 정한다. 펀드코드처럼 목록의 값마다 호출하는 인자는 아래 `query_each` 로 둔다. 운영 중에는 서버가 혼자 쿼리를 호출하므로 이 밖의 값(담당자가 업데이트 때마다 엑셀에 새로 적는 조회 조건, 다른 쿼리의 결과)은 만들 수 없다. `query_link.py` 는 그런 값을 거절하므로, 그런 인자가 있으면 개발자에게 알리고 그 표의 연결을 멈춘다.

맞는 쿼리가 없으면 `query_requests.md` 에 등록 요청을 적고, 사용자가 이 파일을 AX 팀에 넘긴다(전산의뢰). 요청마다 표 정의의 `id` 와 만들 표 이름, 매개변수 값이 든 셀을 함께 적는다. 등록 쿼리는 AX 팀이 승인하므로 값 대조는 하지 않는다.

등록 번호를 기다리지 않는다. 6 · 7단계는 엑셀 저장값으로 할 수 있으므로 먼저 한다.

### 6. 저장 설계

엑셀 영문 이름은 Claude 가 엑셀 이름과 내용으로 먼저 제안하고, 표 이름 예시와 함께 「이렇게 저장할까요?」로 묻는다. 예: 「엑셀 영문 이름을 `stock_sample` 로 해서 표 이름을 `stock_sample__calc__daily` 처럼 저장할까요? 표 이름의 앞 글자가 되므로 샌드박스에 표를 만든 뒤에는 바꾸지 않습니다.」 영문 소문자 · 숫자 · `_` 만 쓴다. 샌드박스 표는 11단계에서 만들므로 그 전까지는 이름을 바꿔도 잃는 데이터가 없다.

쓸 수 있는 스키마를 샌드박스 스킬(`managing-sandbox`)의 `schemas` 로 조회해 BS · WS 같은 코드로 보이고 개발자에게 고르게 한다. 고르는 기준은 그 엑셀을 쓰는 본부다. 고른 스키마를 `--schema`, 영문 이름을 `--slug`, `sources.json` 을 `--sources` 로 넘겨 `table_plan.py` 로 `table_plan.json` 을 만든다. 표 이름은 `{엑셀}__{단계}__{대상}` 이고, 단계는 `raw_winus` · `raw_wfs` · `raw_manual` · `fixed` · `calc` · `stat` 이다.

- 원천 표의 열마다 결과 계산이 읽는지와 0 · 빈 값 비율을 `table_plan.py columns` 로 보이고, 계산이 읽지 않는 열을 저장할지 묻는다.
- 결과표에 뜻이 다른 행 구간이 섞여 있는지 확인한다. `table_plan.split_points` 는 수식이 크게 바뀌는 행만 찾고 다른 시트를 복사해 붙인 구간은 놓칠 수 있다. 그래서 찾은 행이 없어도 행이 많은 결과표는 개발자에게 구간이 있는지 묻는다. 구간이 있으면 3단계로 돌아가 표 정의를 나눈다.
- WINUS · WFS 원천 표는 primary key 없이 만든다. 저장은 기준일 범위를 통째로 교체하고 조회는 모든 열로 정렬해 읽으므로 key 가 없어도 행이 겹치거나 빠지지 않는다. 등록 쿼리의 결과는 여러 테이블을 잇거나 묶은 값이라 원본 테이블의 key 를 그대로 쓸 수 없다.
- 통계 표(`stat`)는 결과표 정의의 소계 항목을 `target` 으로 묶어 대상마다 하나 생긴다. 열은 이름 글자 열 · 묶는 열 · 값 열이고, 열 이름은 결과표 열 이름을 그대로 쓴다. 통계 표는 저장하지 않는다.

`table_plan.py` 는 원천 표를 언제나 연결 대기로 만들므로, 6단계부터 다시 할 때는 8단계 쿼리 연결도 다시 실행한다.

### 7. 계산 이전과 엑셀 대조

[calc-guide.md](calc-guide.md) 대로 결과표와 통계 표를 표 · 열 이름 기준의 Python 코드 `calc.py` 로 옮긴다. `scripts/verify_calc.py` 로 엑셀 저장값과 셀 단위로 대조하고, 합격(종료 코드 0)해야 다음으로 간다. 통계 표는 행의 이름 글자와 묶는 열 값으로 엑셀 소계 행을 찾아 같은 열의 셀과 맞춘다. 대조 결과 파일에 다른 셀, 빠진 셀, 다른 소계 칸, 빠진 소계 행이 적힌다.

### 8. 쿼리 연결

새 구조 임시 실행은 실제 WINUS · WFS 응답으로 하므로, 등록 번호가 있는 원천 표를 여기서 연결한다. `searching-winus` 로 한 기준일의 응답을 받아 파일로 두고 `scripts/query_link.py` 로 연결한다. 어느 응답 열이 어느 표 열인지는 스크립트가 찾지 않고 Claude 가 정한다.

1. 행을 짝짓는 키 열(`--key 엑셀열 응답열`, 여러 열이면 여러 번)만 주고 실행한다. 결과의 `samples` 에 대응이 빠진 표 열과 응답 열의 값이 몇 개씩 나온다.
2. Claude 가 값과 열 이름을 보고 표 열마다 응답 열과 단위 변환을 제안한다. 변환은 `same`(그대로), `/1e8`(억으로 나누기), `*100`, `round(/1e6)`(백만으로 나눠 사사오입)처럼 배수로 적는다. 제안은 「표 열 · 응답 열 · 변환」 표로 보이고 개발자에게 확인받는다. 모르는 열은 짐작하지 않고 개발자나 엑셀 담당자에게 묻는다.
3. 확인받은 대응을 `--map 엑셀열=응답열[:변환]` 으로 넘겨 다시 실행한다. 결과의 `checked` 에 열마다 같은 행 수와 값이 다른 행이 나온다. 값이 모두 같으면 「쿼리 연결 대기」를 푼 `table_plan.json` 이 나온다.
4. 값이 다른 행이 있으면 그 행을 개발자에게 보인다. 대응이 틀렸으면 고쳐 다시 실행하고, 엑셀 저장 뒤 원천 값이 바뀐 것처럼 대응은 맞다고 개발자가 정하면 `--accept` 를 붙여 다시 실행한다. `repeated_keys` 가 0 이 아니면 응답 행 여럿이 같은 키라 짝을 정할 수 없으니 키 열을 추가한다.

`--out-registry` 파일은 샌드박스에 넣지 않는다. 9단계 초기 적재가 엑셀 목록 표를 다시 만들기 때문이다. 열 구성이 달라 표를 다시 만들어야 하면 개발자에게 알린다.

결과의 `unmatched_rows` 는 키가 응답에 없는 엑셀 행 수다. 0 이 아니면 대기를 풀지 않고 개발자에게 알린다. 엑셀이 레코드 하나를 두 줄로 보이거나(예: 펀드 줄 아래 BM 줄) 머리글 · 합계 줄이 표 안에 섞인 원천 표다. 이런 시트는 스킬이 자동으로 찾지 않는다. 개발자가 그 표의 엑셀 행을 응답 모양으로 바꾸는 코드를 쓴다.

연결을 마치면 개발자에게 알린다. 「운영 중 원천 표나 결과 표가 그날 0건이면 그 기준일은 저장하지 않고, 화면에 그 표 이름과 함께 실패를 보입니다. 데이터가 아직 들어오지 않은 날을 잡기 위해서입니다. 빈 날이 정상인 표가 있으면 `upload.py` 의 0건 검사를 그 표만 고치면 됩니다.」 묻지 않고 알리기만 한다.

기준일 하루의 전체 조회가 쿼리 실행 시간 상한을 넘으면, 그 원천 표에 `query_each` 를 적어 목록의 값마다 한 번씩 순서대로 호출하게 한다. 예: `{"arg": "t_fund", "table": "<결과표 행 목록 표>", "column": "펀드코드", "pad": 4}`. 목록은 그 기준일의 수기 입력 표에서 읽고, 빈 값과 중복은 빼며, `pad` 자리로 앞에 0 을 채운다. 펀드코드 인자가 없는 쿼리는 분류처럼 정해진 값으로 나눈다. 예: `{"arg": "t_gubun", "values": ["1", "2", "9"]}`. 이때는 가장 큰 값 하나로 먼저 호출해 시간 안에 끝나는지 확인한다. 값 하나의 0건은 넘어가고, 합친 결과가 0건이거나 호출이 하나라도 실패하면 그 기준일은 저장하지 않는다. 담당자가 행을 추가하거나 지우는 수기 입력 표에는 `row_config: true` 를 적는다.

5단계에서 등록 요청한 표가 아직 등록되지 않았으면, 「등록 뒤에 이어서 하기를 권장합니다」라고 안내하고 개발자에게 두 가지 중 고르게 한다.

- 기다린다(권장). `explain_results.json` 과 같은 폴더에 인계 문서 `HANDOFF-<엑셀 영문 이름>.md` 를 남기고 멈춘다. 인계 문서에는 전산의뢰한 쿼리(표 이름 · 화면 번호 · 의뢰 번호), 끝낸 단계, 다시 시작할 단계(8단계)를 적는다. 등록 번호가 오면 새 세션이 이 문서를 읽고 8단계부터 이어서 하고, 8단계를 시작할 때 문서를 지운다. 등록에는 며칠이 걸려 그사이 세션이 끝나기 때문이다.
- 등록된 표만 연결하고, 등록되지 않은 표는 엑셀 저장값을 그대로 써서 임시 실행을 진행한다. 개발자가 결과를 바로 보고 싶을 때 쓴다. 남은 표의 등록 번호가 오면 그 표를 연결하고 9~10단계를 다시 한다. 이미 샌드박스에 쌓았으면 11단계의 쌓기도 그 기준일에 다시 한다.

### 9. 새 구조 임시 실행

`review_run.py run` 으로 새 구조 전체를 실행한다. 샌드박스 대신 임시 저장소(`review/store/`)에 저장하는 것만 다르고, 나머지는 운영과 같은 코드가 실행된다. 대화에서는 「새 구조를 임시로 만들어」라고 말한다.

- 실행할 때마다 `review/store/` 를 비우고 새로 만든다. 초기 적재를 넣고, 화면 서버 API 로 입력 양식을 내려받아 그대로 올린다. 업로드가 양식 검사, WINUS · WFS 조회, 계산, 저장을 운영과 똑같이 한다. 연결을 기다리는 원천 표는 조회하지 않고 엑셀 저장값을 쓴다.
- 업로드 뒤 검토 기준일 결과표와 통계 표를 엑셀 저장값과 대조해 `review/verify_report.json` 에 쓰고, 검토 엑셀 `review/<엑셀 영문 이름>-review.xlsx` 를 쓴다. 검토 엑셀에는 원천 · 수기 입력 · 고정값 표가 `raw_` 시트, 결과표가 `cal_` 시트, 통계 표가 `stat_` 시트로 들어가고 소계 행은 없다.
- 불합격이면 다른 칸 목록을 열마다 원인과 예시 값과 함께 개발자에게 보이고, 개발자가 엑셀 담당자에게 아래 중 하나를 묻게 한다. Claude 가 정하지 않는다. 엑셀에 붙여 넣은 화면 값은 응답과 다를 수 있다. 예를 들어 화면은 소수 둘째 자리까지만 내려받고, 응답이 빈 값으로 주는 칸을 화면은 0 으로 보인다.
  - 엑셀과 같게 맞춘다(예: 소수 둘째 자리로 맞춘 뒤 계산, 빈 값은 0).
  - 응답 값 그대로 보인다.
  - 담당자가 정한 다른 기준을 따른다.

  답에 맞게 `calc.py` 를 고치고 7단계부터 다시 한다.
- 보고서의 `source_changes` 에서 `only_excel` · `only_fetched` 가 0 이 아닌 원천 표는 엑셀 저장 뒤 원천 값이 바뀐 표다. 그 표 이름과 그 표에서 오는 결과 칸을 「엑셀 저장 뒤 원천 값이 바뀌어 생긴 차이일 수 있는 칸」으로 10단계 문구와 함께 알린다. 담당자가 그 차이를 계산 오류로 보고 검토를 되풀이하지 않게 하기 위해서다.

### 10. 결과표 검토

기존 수기 작성 엑셀을 만드는 엑셀 담당자에게 검토 엑셀을 보내 비교해 달라고 한다. Claude 는 합격 여부를 판단하지 않고, 「맞다」는 답이나 고칠 곳을 받는다. 문구 예:

> 새 구조를 임시로 만들어 계산 결과를 엑셀에 저장했습니다. `raw` 시트는 원천 데이터, `cal` 시트는 수식 계산 후 결과표입니다. 소계 · 합계 같은 통계 표는 별도 시트에 저장했습니다. 결과를 기존 수기 작성 엑셀과 비교해, 값이 이상한 곳이 있는지 확인해 주세요.

- 열 이름이나 열 구성을 고치면 6단계 `table_plan.json` 부터(8단계 쿼리 연결 포함), 값을 고치면 7단계 `calc.py` 부터 다시 하고, 9단계를 다시 실행한다.
- 검토 엑셀을 보낸 뒤 답을 받기 전에는 9단계를 다시 실행하지 않는다. 다시 실행하면 원천을 새로 받아 저장소와 검토 엑셀이 바뀌므로, 담당자가 보지 않은 내용이 승인되지 않게 하기 위해서다. 다시 실행했으면 새 검토 엑셀을 다시 보내고 그 엑셀에 대한 답을 받는다.
- 「맞다」를 받으면 `review_run.py approve` 로 그때의 저장소와 검토 엑셀을 `review/approved/` 로 복사한다. 11단계는 이 승인본만 쌓는다.

### 11. 샌드박스에 쌓기

샌드박스에 저장할지 묻는다. 통계 표는 `calc.py` 로 언제든 다시 계산할 수 있으므로 저장을 제안하지 않는다. 문구 예:

> 샌드박스(AX DB)에 저장할까요? 통계 표는 `calc.py` 로 언제든 다시 계산할 수 있어 저장 대상에 넣지 않았습니다. 통계 표로 대시보드 화면을 만들려면 `calc.py` 의 통계 표 계산 코드를 쓰면 됩니다.

개발자가 통계 표도 저장하고 싶다고 하면 `table_plan.json` 에서 그 통계 표의 단계를 `calc` 로 바꾸고 9단계부터 다시 한다.

1. 표를 만든다. `table_plan.py requests` 로 표마다 만들기 요청 파일을 쓰고, 샌드박스 스킬의 `create --spec` 으로 만든다. 다시 시작한 작업이면 먼저 샌드박스 스킬의 `describe` 로 있는 표의 열을 읽어 `{표 이름: 열 목록}` 파일로 모으고 `table_plan.py compare` 로 대조한다. 같은 표는 다시 만들지 않고 다른 표는 묻는다. 공용 표 `excel_registry` 가 옛 `summaries_json` 열만 더 있어 「다름」으로 나오면 그 열을 지우지 않고 그대로 둔다. 다른 엑셀이 쓰는 공용 표이고, `upsert` 는 보낸 열만 고치기 때문이다.
2. `review_run.py sandbox-requests` 로 승인본에서 요청 파일을 만든다. 이름의 번호가 실행 순서다. 1번은 엑셀별 표의 기준일 범위 교체(`overwrite`), 2번은 고정값 표와 엑셀 목록 표의 `upsert`, 3번은 업로드 이력의 완료 행 덧붙이기(`insert`, `append`)다.
3. 확인 질문이 많아지지 않게, 확인 절차가 있는 1번과 2번 파일만 `--confirm` 없이 실행해 미리보기를 모은다. 3번은 확인 절차 없이 바로 들어가므로 미리보기를 모을 때 실행하지 않는다. 모은 미리보기는 줄이지 않고 파일마다 스크립트 출력 그대로 한 메시지에 이어 보인다. 「내 테이블 기록에 없음」 줄이 있는 파일은 맨 앞에 두고 질문 첫머리에 그 사실을 적는다. 질문은 본문으로 한 번 묻는다.
4. 개발자가 실행을 고르면 번호 순서로 `--confirm <확인값>` 을 붙여 실행한다. 하나라도 실패하거나 확인값이 달라졌으면 멈추고 뒤 번호는 실행하지 않는다. 앞 파일이 모두 성공한 뒤에만 3번을 한 번 실행한다. 3번이 있어야 화면이 그 기준일을 완료로 보므로, 일부 표가 빠진 기준일이 완료로 보이지 않게 하기 위해서다.
5. 쌓은 뒤 `sandbox_load/select/` 의 조회 요청마다 샌드박스 스킬 `select --request <파일> --all --out <폴더>/<요청 파일 이름에서 select_ 를 뺀 이름>` 으로 받고, `review_run.py check-sandbox` 로 승인된 검토 엑셀과 대조한다. 다른 곳이 나오면 개발자에게 보인다. 임시 저장소와 실제 샌드박스의 동작 차이(소수 · 날짜 표현, 교체 범위)는 이 대조로 찾는다.

샌드박스에서 업로드 처리를 다시 실행하지 않는다. 대화 중 Claude 가 실행하는 샌드박스 쓰기는 샌드박스 스킬 스크립트로만 하고, 화면 서버의 업로드 처리는 로그인 토큰이 있어야 실행되기 때문이다.

### 12. 화면 예시(물을 때만)

화면을 먼저 제안하지 않는다. 개발자가 화면을 원하거나 「저장된 값은 어떻게 고치느냐」처럼 물을 때만, 가짜 데이터로 만든 예시 화면을 보여 준다.

- 화면을 켤 대시보드 저장소는 개발자의 대시보드 저장소가 있으면 그 저장소의 복사본, 없으면 `dashboard-template` 복사본이다. 복사본은 세션 임시 폴더에 둔다.
- [templates/README.md](templates/README.md) 의 복사 절차대로 `templates/` 를 기능 폴더로 복사하고, 그 기능 폴더에 `examples/stock-sample/` 의 파일을 넣어 켠다. 예시의 `router.py` 는 샌드박스와 등록 쿼리 서버를 호출하지 않고 `examples/stock-sample/store/` 의 가짜 데이터로 실행된다. 화면에서 양식 내려받기 → 수기 입력 고치기 → 업로드로 저장된 값을 고치는 방법을 보인다.
- 보여 준 뒤 복사본을 지운다.

복사할지와 어떻게 고칠지는 개발자가 정한다. 서버 코드를 고치려는 개발자에게는 아래 제약을 알린다. 한 대시보드의 여러 기능은 같은 모듈 이름(`api` · `store` · `upload`)을 쓴다. 모듈 이름이 같아서, 한 기능의 서버 코드만 고치면 먼저 읽힌 쪽 코드가 모든 기능에 쓰인다.

## 개발 뒤의 구조 변경

변경 절차는 따로 없고 개발자가 직접 고친다. 아래 원칙을 지킨다.

- 열 추가는 기존 표에 열을 추가하고, 과거 기준일의 새 열은 빈 값으로 둔다.
- 표 이름과 열 이름은 응용화면이 쓰는 약속이므로, 바꾸기 전에 응용화면 개발자에게 확인한다.
- 계산 코드를 고치면 엑셀 대조를 다시 실행하고, 과거 기준일 결과는 다시 계산하지 않는다.

## 실행 명령

스크립트는 PowerShell 에서 아래 형식으로 실행한다. 하위 명령과 인자는 스크립트 첫머리 설명과 `--help` 에 있다.

```powershell
uv run --system-certs --no-project --with-requirements "<스킬>\scripts\requirements.txt" python "<스킬>\scripts\table_plan.py" <인자>
```

| 단계 | 명령 |
|---|---|
| 1~3 | 분석기 `explain_cell.py "<엑셀>" --all --out explain_all.html`, 이어서 `explain_cell.py "<엑셀>" --all --results explain_results.json --facts --out explain_facts.json`(분석기 스킬 폴더의 `requirements.txt` 로 실행) |
| 1~3 | `table_plan.py check "<엑셀>" --results explain_results.json --facts explain_facts.json` |
| 6 | `table_plan.py explain_results.json --slug <엑셀 영문 이름> --sources sources.json --schema <스키마> --out table_plan.json`, `table_plan.py columns` |
| 7 | `verify_calc.py "<엑셀>" --plan table_plan.json --results explain_results.json --calc calc.py --base-date YYYY-MM-DD --out verify_report.json` |
| 8 | `query_link.py` |
| 9 | `review_run.py run "<엑셀>" --plan table_plan.json --results explain_results.json --calc calc.py --base-date YYYY-MM-DD --dir review` |
| 10 | `review_run.py approve --dir review` |
| 11 | `table_plan.py requests` · `compare`, `review_run.py sandbox-requests --dir review/approved --plan table_plan.json --out sandbox_load`, `review_run.py check-sandbox --selected <폴더> --plan table_plan.json --calc calc.py --base-date YYYY-MM-DD --dir review` |
