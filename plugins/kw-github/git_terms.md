# git 용어표

개발자에게 하는 말에 적용한다. 스킬과 지시문은 git 용어를 그대로 쓴다(사용자 결정, 2026-10-21).

단어만 그 자리에 바꿔 끼우지 않는다. 바꾼 문장이 어색하게 읽히면 문장을 다시 쓴다. 용어를 넣어도 개발자가 얻는 정보가 없는 문장(예: 아무 일도 하지 않았다는 알림)에는 용어를 쓰지 않고 "새로 저장할 변경이 없습니다" 처럼 쉬운 말로 쓴다.

용어를 정의하는 문장("~라고 불러요", "~라는 뜻이에요")은 쓰지 않는다. 대신 용어를 쓴 문장에 그 행동의 결과를 쉬운 말로 붙여, 반복해서 듣는 동안 뜻이 드러나게 한다. 개발자가 뜻을 물으면 그때만 짧게 답한다.

## 영어 그대로 쓰는 용어

| git 용어 | 쓰는 방법 | 개발자에게 하는 말 예 |
|---|---|---|
| commit | 그대로 쓰고 "시점을 저장해 되돌릴 수 있다"는 결과를 붙인다. | "commit 해 두었습니다. 이 시점으로 코드를 되돌릴 수 있습니다." |
| push | push 는 나올 때마다 "push(업로드)" 로 쓴다. | "GitHub 에 push(업로드)했습니다. 페이지를 새로고침하면 보입니다." |
| main | "팀이 함께 보는 main" 처럼 쓴다. 공유 대시보드 레포에서는 main 대신 "공유 코드" 라고 쓴다. | "팀이 함께 보는 main 에 반영했습니다." (공유 대시보드 레포: "공유 코드에 반영했습니다.") |
| branch | "기존 코드는 두고 복제한 새 branch" 처럼 쓴다. | "기존 코드는 두고 복제한 새 branch 에서 작업하겠습니다." |

## 쉬운 말로 바꾸는 용어

| git 용어 | 문장에 쓰는 말 |
|---|---|
| repo | GitHub 코드 저장소 |
| local | 내 PC |
| merge | 반영 (예: "main 에 반영했습니다") |
| conflict | "팀원도 같은 줄을 고쳐서 어느 쪽을 남길지 골라 주셔야 합니다" 처럼 상황을 그대로 말한다 |
| .gitignore | 업로드 제외 목록 |
| PR | 검토 요청 |

## 말하지 않는 용어

remote, fetch, pull, rebase, clone, issue 는 개발자에게 말하지 않는다. 개발자가 직접 할 일이 없는 단계이기 때문이다. 필요하면 "팀원이 바꾼 내용을 받아왔습니다" 처럼 결과만 말한다. 이슈는 Claude 가 뒤에서 작성한다.

용어를 한글로 옮겨 적지 않는다(커밋, 푸시, 브랜치, 레포, 머지, 리베이스).
