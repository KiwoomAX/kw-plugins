# 사용자의 코드에 넣을 때

사용자의 코드(스크립트·서비스·예약 작업)에 DBGateway 호출을 넣을 때 읽는다. 요청 코드는 SKILL.md 「코드」의 `fetch`·`fetch_retrying`을 그대로 쓰고, 아래로 쿼리를 잇고 거절을 처리한다.

## 쿼리를 잇는 예

```python
# id만으로는 무엇인지 알 수 없으므로 목차의 이름을 상수 이름에 남긴다. 아래 id는 예시이고, 실제 id는 목차에서 고른다.
Q_기준일_비교일자 = 1
Q_당사_ETF_순자산 = 5
Q_내부코드명 = 10

날짜 = fetch_retrying(Q_기준일_비교일자, {"오늘": "20260915"})["rows"][0]
당사_etf = fetch_retrying(Q_당사_ETF_순자산, {
    "d0": 날짜["기준일"], "d1": 날짜["전일"],
    "d2": 날짜["당사전월말"], "d3": 날짜["당사전년말"],
    "cls": "44",
})
카테고리명 = fetch_retrying(Q_내부코드명, {"cls": "GT002", "codes": ["001", "002"]})  # 코드는 분류에 맞게: GT002는 카테고리
```

- 결과 열 이름은 등록된 SQL의 열 별칭과 대조해 쓴다.
- `async def` 안에서는 `httpx.AsyncClient`를 쓰고 앱 종료 시 닫는다. 동기 호출은 이벤트 루프를 차단한다.
- 코드를 쓴 뒤 가능하면 한 번 실제로 불러 결과 행 수와 열 이름을 확인하고 사용자에게 알린다.

## 거절

실패 응답은 422·405를 빼면 모두 `{"kind": "…", "code": "…", "detail": "…"}` 모양이다. 무엇을 할지는 `code`로 정하고, 표에 없는 `code`는 `kind`로 정한다. `detail`은 사용자에게 보일 문장이라 그대로 전하고, 프로그램이 읽어 판단하지 않는다.

| 상태 | `kind` | 뜻과 할 일 |
|---|---|---|
| 401 | 신원 거절 | 접근 키가 틀렸거나 폐기됨(`unidentified`). DBGateway가 키 없는 요청을 받지 않으면 키가 없을 때도 온다. 같은 요청을 재시도하지 않고 [access-key.md](access-key.md)의 순서를 안내한다 |
| 400 | 범위 초과 거절 | 요청을 고쳐야 받는다. 없는 id(허용되지 않은 쿼리의 id도 없는 id와 같게 거절된다), 인자 누락·모르는 인자, 스칼라 인자에 배열, 빈 배열, 목록 인자 개수 초과, 결과 3만 행 초과(`too_many_rows`), 실행 상한을 넘긴 조회, [table-query.md](table-query.md)의 거절. 같은 요청을 재시도하지 않는다. `detail`이 나눠 질의하라고 하면 그대로 나눠 부른다 |
| 422 | (없음) | 본문 형식 오류(값이 문자열·문자열 배열이 아님, 본문의 모르는 항목) 또는 경로의 id가 정수가 아님. 본문은 `{"detail": [{"type": "…", "loc": ["body", "args", "<인자 이름>", …], "msg": "…"}]}`이고, `loc`의 셋째 칸이 문제의 인자 이름이다. 보낸 값은 응답에 실리지 않는다 |
| 405 | (없음) | 주소 뒤에 인자를 붙여 GET으로 부르는 이전 방식으로 불렀음(DBGateway가 그 방식을 거둔 뒤에 옴). 본문은 `{"detail": "Method Not Allowed"}`다. 같은 요청을 재시도하지 않고 POST 본문으로 바꾼다. 목록 인자는 같은 이름을 반복하지 않고 문자열 배열로, 숫자도 문자열로 보낸다 |
| 429 | 혼잡 거절 | 이 사람의 몫을 다 씀. 사람당 대기 조회 수·초당 요청 수 상한 초과, 큐 대기 예상 초과는 잠시 뒤 다시 보낸다. 아래 두 `code`는 다르게 처리한다 |
| 429 | 혼잡 거절 | `source_time_exceeded`: 이 사람이 쓸 수 있는 원본 사용 시간을 다 씀. 늦춰 보내도 다시 찰 때까지 풀리지 않는다. `Retry-After`의 초만큼 기다리거나, 그 시간이 길면 다시 보내지 않고 거절을 그대로 올린다. 기간이나 목록을 줄이면 한 번에 쓰는 원본 시간이 준다 |
| 429 | 혼잡 거절 | `caller_stopped`: 운영자가 이 사람의 조회를 중지함. `detail`에 운영자가 적은 사유가 있다. 언제 풀리는지 알리지 않으므로 다시 보내지 않고 거절을 그대로 올린다. `detail`과 함께 AX팀에 문의하라고 전한다 |
| 503 | 혼잡 거절 | 원본이 받을 수 없음(원본 불통·차단, 운영자의 원본 조회 중지 `source_stopped`, 이 쿼리가 쓰는 WINUS 계정을 지금 쓸 수 없음 `account_unavailable`). 언제 풀릴지 DBGateway도 모르므로 정한 횟수만 다시 보내고, 그래도 같으면 거절을 그대로 올린다 |
| 503 | 판정 불능 | DBGateway가 요청을 받을지 거절할지 정하지 못함. 일시적일 수도, DBGateway 쪽 문제일 수도 있다. 한 번만 다시 보내고, 같으면 거절을 그대로 올린다. `detail`과 함께 AX팀에 알리라고 전한다 |
| 그 밖 5xx | 형식 미확인 | DBGateway나 DB 쪽 오류 |

`wait_before_retry`가 이 표의 다시 보내기 규칙을 코드로 옮긴 것이다. 다시 보낼 때는 응답 헤더 `Retry-After`가 있으면 그 초만큼 기다리고, 없으면 몇 초씩 늘려 가며 정한 횟수만 보낸다. `MAX_WAIT_SECONDS`는 사람이 결과를 기다리는 조회 기준이라, 자동으로 실행되는 작업이면 늘려도 된다.

**예약 작업처럼 자동으로 실행되는 코드는 알려 줄 사람이 없다.** 호출한 쪽이 거절(`Refused`)을 받아 기록을 남기거나 담당자에게 알리게 짠다.
