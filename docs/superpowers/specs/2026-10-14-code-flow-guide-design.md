# 코드 동작 흐름 안내 화면 스킬 설계 (2026-10-14)

스킬 `explaining-code-flow` 는 레포 이름을 받아 HTML 두 개를 함께 만든다. 개발자용 안내 화면(`index.html`)은 기능마다 버튼을 누른 뒤 자료가 어디로 오가는지를 움직이는 그림으로 보여 준다. 이 화면을 읽는 사람은 바이브 코딩으로 레포를 만든 사람이고, 함수 이름과 API 개념을 모른다고 가정한다. 사용자 설명서(`manual.html`)는 같은 분석 결과로 화면의 각 항목과 버튼의 뜻을 보여 주며, 화면을 쓰는 사람이 읽는다(「사용자 설명서」 절).

## 목적

스킬은 실제 화면의 버튼과 그 뒤의 자료 이동을 한 화면에 함께 보여 준다. 바이브 코더는 자기 레포가 어느 DB 에서 무엇을 읽고 어느 서버를 거쳐 결과를 내는지 모르고, 코드 위치를 알려 주어도 읽지 못하기 때문이다.

주 세션(Claude)이 아래 시제품을 손으로 만들었고, 사용자가 검토를 마쳤다. 시제품은 `~/02.github/flow_guide/` 에 있고 git 레포가 아니다.

| 시제품 | 대상 레포 | 범위 |
|---|---|---|
| `esg_movie.html` | Kiwoom-ESG (main `ac717211`) · llm-manager (`feat/llm-manager-chat-function` 브랜치 `2b2d3b6`) | 「회사 평가 실행」 기능 하나 |
| `wholesale_movie.html` | wholesale-dashboard (main `0758137`) | 메뉴의 모든 기능, 장면마다 실제 화면 캡처와 줌 |

줌은 화면 칸의 캡처를 누를 버튼 쪽으로 확대했다가 결과 쪽으로 다시 확대하는 동작이다. JSON 에서는 장면의 `screen.start` · `screen.end` 사각형이 확대할 곳을 정한다.

스킬은 시제품을 만든 순서를 절차로 옮기고, 시제품 템플릿에서 레포별로 손으로 넣은 값을 JSON 입력으로 옮긴다.

## 위치

스킬은 `plugins/kw-dashboard/skills/explaining-code-flow/` 에 둔다. 스킬 이름과 위치는 사용자가 정했다(2026-10-14). 사용자는 kw-dashboard 를 사내 공용 기능을 모으는 플러그인으로 쓰고, 기능마다 스킬을 나눈다.

| 파일 | 내용 |
|---|---|
| `SKILL.md` | 절차와 고정 명칭표와 문장 규칙 |
| `analysis-prompt.md` | 기능 하나를 맡는 분석 서브에이전트의 지침과 출력 JSON 형식 |
| `tips-prompt.md` | 「알아 둘 점」을 코드에서 찾아 근거와 함께 적는 지침 |
| `areas-prompt.md` | 화면 하나를 맡는 항목 서브에이전트의 지침과 출력 JSON 형식(「화면 항목 목록과 설명 대조」 절) |
| `scripts/run_repo.py` | 사내 인증서를 준 명령 실행과 Node 화면의 설치 · 개발 서버 실행 · 종료 |
| `scripts/capture.py` | 화면 요청을 가로채 레포 파일과 가짜 데이터로 응답하며 기능마다 캡처하는 단계 |
| `scripts/render.py` | JSON 을 검사하고, 출력 폴더를 받아 두 템플릿으로 `index.html` 과 `manual.html` 을 함께 만드는 단계 |
| `scripts/movie_template.html` | 개발자용 안내 화면 템플릿. 시제품 템플릿에서 레포별 값을 뺀 사본 |
| `scripts/manual_template.html` | 사용자 설명서 템플릿 |

플러그인 설명은 `plugins/kw-dashboard/.claude-plugin/plugin.json` 과 `.claude-plugin/marketplace.json` 두 곳에 같은 문장으로 있고, 지금은 대시보드 스킬만 설명한다. 이 스킬을 넣을 때 두 파일의 `description` 에 「`explaining-code-flow` 는 레포의 기능별 동작 흐름을 움직이는 개발자용 안내 화면과 사용자 설명서로 만든다」는 문장을 함께 넣는다. 스킬의 description 에도 「사용자 설명서」 · 「사용 설명서」를 트리거 말로 넣는다.

kw-plugins 는 윈도우 PowerShell 을 전제한다. 스크립트는 모두 파이썬이고 하위 명령을 `subprocess` 의 인자 목록으로 실행하므로, PowerShell 5 · 7 의 따옴표와 변수 문법에 영향받지 않는다. 스크립트 자신의 의존성(Playwright)은 `uv run --no-project --with` 로 임시 환경에 설치하고 PC 전역 파이썬에는 설치하지 않는다.

| 순서 정하기 | 주 세션이 레포 전체의 큰 흐름(데이터를 쓰는 곳과 읽는 곳, 화면의 단계 번호와 비활성 조건)을 먼저 읽고 기능 순서를 정한다 | 기능마다 판정 기준과 근거 `파일:줄` 이 있는 순서표가 있다 |
| 순서 검토 | 주 세션이 순서표를 「사람이 화면을 보는 순서 · 실제로 움직이는 순서」와 대조해 고친 뒤, 순서표를 사용자에게 알리고 확인을 기다리지 않고 진행한다(사용자 결정 2026-10-16) | 답에 순서표가 있고, 코드 파일 순서를 근거로 쓴 줄이 없다 |
| 기능별 분석 | 주 세션이 기능마다 분석 서브에이전트를 동시에 실행하고, 같은 때에 화면마다 항목 서브에이전트도 실행한다(「화면 항목 목록」 줄). 분석 서브에이전트는 `analysis-prompt.md` 에 따라 화면 코드와 백엔드의 저장 · 조회 코드를 함께 읽고, 장면 · 동작 · 화면 표기 · 캡처 계획 · 가짜 데이터를 근거 줄과 함께 낸다 | 모든 동작에 `파일:줄` 근거가 있고, 주 세션이 출력 JSON 형식을 검사한다 |
| 화면 항목 목록 | 항목 서브에이전트는 기능 분석과 따로 `areas-prompt.md` 에 따라 화면에 렌더되는 항목을 모두 나열하고, 항목마다 뜻을 닿은 데까지 근거와 함께 낸다(「화면 항목 목록과 설명 대조」 절). 주 세션은 기능 분석의 「근거 대조」를 항목 뜻에도 적용한다 | 조건부로 그려지는 줄 · 조건부 class · 이벤트 처리 줄마다 항목이나 제외 사유가 있고, 주 세션이 뜻 문장 몇 개를 근거 줄과 대조한다 |

| 알아 둘 점 검토 | 주 세션이 근거 줄을 열어 대조하고, 화면 문구 재진술 · 핵심으로 잘못 올린 참고 · 빠진 핵심 · 장면 사이 중복을 고친다 | 검토에서 고친 항목 수를 답에 적는다 |
| 설명 대조 검토 | 주 세션이 항목마다 장면 · 알아 둘 점 중 어디에서 설명되는지 대조하고, 빠진 항목을 채운다. 장면이 없는 버튼이 있으면 그 기능의 분석 서브에이전트를 빠진 버튼 목록과 함께 다시 실행한다 | 빠진 항목 수와 채운 방법을 답에 적는다 |
| 화면 캡처 | 화면 코드를 띄우고 가짜 데이터로 응답하며 기능마다 캡처한다(「화면 캡처」 절). 0번 화면 둘러보기의 화면도 캡처하고 항목마다 위치를 측정한다 | 모든 장면과 둘러보기 화면에 캡처 또는 실패 문구가 있고, 띄운 개발 서버가 남지 않는다 |
| JSON 합치기 | 주 세션이 분석 결과와 항목 목록에 캡처 결과(이미지 경로, 사각형, 실패 문구)를 넣어 `flow.json` 하나로 만든다. 번호는 `render.py` 가 렌더할 때 위치를 찾은 항목에만 위에서 아래, 왼쪽에서 오른쪽 순서로 매긴다 | `render.py` 의 필드 검사를 통과한다 |
| 렌더 | `render.py` 가 `flow.json` 하나로 개발자용 `index.html` 과 사용자 설명서 `manual.html` 을 함께 만들고 브라우저로 연다 | 주 세션은 정지 상태를 캡처해 확인하고, 애니메이션 재생은 사용자가 브라우저에서 확인한다 |
| 코드와 다른 점 보고 | 분석 중 발견한 결함(화면 문구와 다른 동작, 알림 없는 실패, 잘못된 표시), 주석과 동작의 불일치, 쓰이지 않는 경로를 고치지 않고 사용자에게 알린다. 결함은 개발자용 안내 화면에만 결함 표시로 싣는다 | 답에 목록이 있다 |
| 결과 알리기 | `index.html` · `manual.html` 경로, 캡처하지 못한 장면과 둘러보기 화면, 뜻을 정하지 못한 항목, 「예시 데이터로 그린 화면」이라는 점, 다른 사람에게 줄 때 HTML 과 `screens/` 를 함께 줘야 한다는 점을 알린다 | 답에 목록이 있다 |

## 고정 명칭표

사용자가 승인한 명칭을 모든 레포에 그대로 쓴다. 템플릿은 노드 종류(`kind`)마다 고정 라벨을 노드 이름 위에 표시하고, 레포별로는 노드 이름(`name`)과 설명(`sub`)만 바꾼다.

| 종류 | 템플릿 고정 라벨 | 노드 이름 예 |
|---|---|---|
| `screen` | 사람이 보는 화면 | 내 PC (브라우저) |
| `server` | 서버 · 프로그램 | 대시보드 서버 · ESG 서버 |
| `db` | 저장소 · DB | Redis 저장소 · AX팀 DB · WINUS |
| `ai` | AI 모델 | Claude · Gemini |
| `web` | 외부 사이트 | 크롤링 대상 사이트 이름 |
| `local` | 팀 공용폴더 | 팀 공용폴더 (Y: 드라이브) |
| `officepc` | 담당자 PC | 담당자 PC |
| `code` | 샘플 데이터 | 샘플 데이터 |
| `clock` | 정해진 시각 자동 실행 | 자동 실행 |

MDB · RDB · 파일 서버는 노드 하나로 묶어 「AX팀 DB」로 부른다. `clock` 노드는 구역 안에서도 시계 아이콘을 유지한다.

구역은 운영 주체를 나타내는 상자이고, 템플릿이 표시 이름을 고정한다. 시제품 템플릿 주석은 구역을 다른 이름으로 부르므로 사본에서는 「구역」으로 통일한다.

| 구역 | 표시 이름 |
|---|---|
| `office` | 내 PC · 사무실 |
| `app` | JSON 의 `appZone` 값 |
| `ax` | AX팀 서버 |
| `winus` | WINUS (회사 DW) |
| `fund` | 우리펀드서비스 |
| `external` | 외부 서비스 |

## JSON 형식

`render.py` 는 아래 필드를 검사하고, 필수 필드가 빠지면 HTML 을 만들지 않고 빠진 필드를 출력한다. 시제품의 `zoneNames` · `dock` · `group` 은 두 시제품 JSON 에서 쓰이지 않거나 템플릿이 읽지 않으므로 옮기지 않는다.

| 위치 | 필드 | 필수 여부 |
|---|---|---|
| 최상위 | `title` · `repo` · `appZone` · `features` | 필수 |
| 기능 | `key` · `name` · `summary` · `nodes` · `scenes` | 필수 |
| 기능 | `screenImg` | 캡처에 성공한 기능만 |
| 노드 | `id` · `name` · `kind` · `zone` · `x` · `y` | 필수(`zone` 은 구역 밖 노드만 생략) |
| 노드 | `sub` | 선택 |
| 노드 | `launch` | 선택(외부 프로그램 · 외부 시스템만) |
| 기능 | `prereq` | 선택(앞 기능을 먼저 해야 하는 조건을 첫 장면 위 띠로 보일 때) |
| 기능 | `chatbot` | 선택(챗봇 기능. 참이면 `nodes` · `scenes` 를 빈 목록으로 두고 「챗봇 기능 안내는 개발 중입니다」만 보인다) |
| 장면 | `title` · `actions` | 필수 |
| 장면 | `screen.startName` · `screen.endName` · `tips` | 필수 |
| 장면 | `auto` | 선택(사람 동작 없이 일어나는 장면) |
| 알아 둘 점 | `text` · `level`(`core` 또는 `ref`) | 필수 |
| 알아 둘 점 | `irreversible` · `defect` | 선택(참 · 거짓) |
| 장면 | `screen.start` · `screen.end` · `screen.startImg` · `screen.endImg` | 캡처에 성공한 장면만 |
| 장면 | `screen.unavailable` | 캡처에 실패한 장면만 |
| 장면 | `nodeOverride` | 선택(장면마다 노드 설명을 바꿀 때) |
| 장면 | `screen.typed` | 선택(입력 동작이 있는 장면) |
| 동작 | `from` · `to` · `icon` · `text` · `say` | 필수 |
| 동작 | `items` | 선택 |
| 최상위 | `tour` | 필수(사용자 설명서의 화면 둘러보기에 넣는 화면 목록이다) |
| 둘러보기 화면 | `key` · `name` · `areas` | 필수 |
| 둘러보기 화면 | `img` | 캡처에 성공한 화면만 |
| 둘러보기 화면 | `unavailable` | 캡처에 실패한 화면만 |
| 항목 | `name` · `meaning` | 필수(뜻을 정하지 못한 항목은 `meaning` 에 닿은 데까지 적는다) |
| 항목 | `no` · `rect` | 캡처가 위치를 찾은 항목만(`render.py` 가 번호를 매기고, `rect` 는 1440×1000 기준 `[x, y, 폭, 높이]`) |

항목 서브에이전트가 내는 찾는 방법(`target`)과 근거 `파일:줄`(`evidence`)은 분석 결과에만 두고 `flow.json` 에 옮기지 않는다. 기능 분석의 `evidence` · `tipsEvidence` 와 같은 방식이다.

노드 좌표는 폭 960, 높이 520 무대의 노드 중심 기준이다. 템플릿은 아래 진행 목록이 한 화면에 들어오도록 세로 좌표를 `30 + (y - 30) × 0.86` 으로 줄여 높이 460 무대에 그린다. 화면 사각형(`screen.start` · `screen.end`)은 1440×1000 캡처 기준의 `[x, y, 폭, 높이]` 다.

## 화면과 문장 규칙

시제품 검토에서 사용자가 정한 규칙을 `SKILL.md` 와 `analysis-prompt.md` 와 `tips-prompt.md` 에 모두 적는다.

| 규칙 | 근거가 된 사용자 지적 |
|---|---|
| 함수 이름 대신 「누가 무엇을 어디에 보낸다」는 서술형으로 쓴다 | 바이브 코더는 함수 이름을 모른다 |
| 버튼 하나를 누른 뒤 일어나는 일을 장면으로 나누고, 화면 표기는 「홈」 메뉴 클릭처럼 버튼 이름으로 쓴다 | 「누를 곳으로 확대」 같은 표기는 어색하다 |
| 동시 처리 건수 제한 같은 내부 수치는 넣지 않는다 | 사용자가 알 필요가 없다 |
| 코드가 하지 않는 동작은 그리지 않고, 값을 하나씩 따로 가져오면 따로 그린다 | 정보를 한 묶음으로 모아 보내는 그림은 코드와 달라 거짓이 된다 |
| 예시 값은 「샘플 데이터」라고 밝힌다 | 실제 집계로 오해한다 |
| 노드 상자는 회색 테두리로 두고, 색은 구역 상자에만 쓴다 | 구역 색과 상자 색이 겹쳐 어지럽다 |
| 왼쪽 세로 띠를 쓰지 않고, 현재 줄은 회색 면으로 표시한다 | 사용자가 띠를 빼라고 했다. 대시보드 스킬의 강제 규칙과도 같다 |
| 「알아 둘 점」은 남색 테두리로 두고, 분홍 같은 튀는 색은 쓰지 않는다. 글자 크기와 표시는 「알아 둘 점」 절을 따른다 | 중요한 정보지만 화려할 필요는 없다 |
| 기능 `summary` 는 서버 · 함수 이름 없이 화면을 쓰는 사람의 시각으로 쓴다(`analysis-prompt.md`) | 설명서의 「이 기능으로 하는 일」에 그대로 보인다(사용자 결정 2026-10-16) |
| 사용자 행동에 영향을 주는 결함은 같은 사실을 사용자 시각의 핵심 알아 둘 점으로도 적는다(`tips-prompt.md`) | 설명서는 결함 표시를 숨긴다(사용자 결정 2026-10-16) |

## 템플릿 변경

스킬 템플릿은 시제품 템플릿에서 레포 id 를 전제한 표를 지우고, 그 표를 읽던 대체 경로도 함께 지운다. 노드의 `kind` · `zone` · `x` · `y` 는 JSON 이 적고, `render.py` 가 빠진 값을 미리 잡는다.

| 대상 | 시제품의 내용 | 스킬 템플릿의 처리 |
|---|---|---|
| `SPOT` 과 `useFeature` 의 좌표 대체 | wholesale 노드 id 별 좌표 | 지운다 |
| `ZONE_BY_ID` 와 `zoneOf` 의 대체 | id 로 구역을 정하는 표 | 지우고 `n.zone` 만 읽는다 |
| `KIND_BY_ID` 와 `kindOf` 의 `'server'` 대체 | ESG · wholesale id 로 종류를 정하는 표 | 지우고 `n.kind` 만 읽는다 |
| `DOCK_BY_ID` 와 `dockOf` 의 붙여 그리기 | 빈 표와 그 처리 | 지운다 |
| `setupShot` 의 화면 칸 숨김 | `screenImg` 가 없으면 칸 전체를 숨김 | `screen.unavailable` 이 있으면 줌 없이 문구를 회색 면에 표시하고, 둘 다 없을 때만 숨긴다 |
| 화면 칸 머리 | 누르는 곳 · 결과 이름만 표시 | 캡처 화면 위에 「예시 데이터로 그린 화면」을 함께 표시한다 |
| `ZONE` · `KIND` · `ICON` | 구역 · 종류 · 자료 아이콘 목록 | 고정 명칭표이므로 남긴다 |

`render.py` 는 레포 의존이 없어 그대로 옮기고, 필드 검사를 넣는다. `render.py` 는 출력 폴더를 받아 `movie_template.html` 로 `index.html` 을, `manual_template.html` 로 `manual.html` 을 만든다. 시제품의 단계 화면(`flow_template.html`)은 옮기지 않는다.

## 화면 캡처

스킬은 백엔드를 실행하지 않고 화면 코드만 띄워, 화면이 보내는 요청에 가짜 데이터로 응답한 상태를 캡처한다(사용자 결정 2026-10-14, email_db 시험 중). 화면에서 일어나는 동작(버튼, 탭, 필터, 목록 그리기, 색과 표시 규칙)은 브라우저 안의 화면 코드가 처리하므로 실제와 같다. 서버 쪽 흐름은 캡처가 아니라 코드 분석으로 그린 흐름 그림과 설명이 보여 준다.

이 방식으로 바꾼 이유는 레포를 실제로 실행하는 방식에서 드러난 문제가 한꺼번에 사라지기 때문이다.

| 실제 실행 방식의 문제 | 가짜 데이터 방식 |
|---|---|
| 캡처에 실제 메일 · 고객 정보가 찍힌다 | 가짜 데이터만 찍힌다 |
| 아웃룩 · Redis 키 · 사내 DB · 고정 포트 같은 실행 조건이 필요하다 | 화면 파일만 있으면 된다 |
| 레지스트리 변경 · 메일 사본 저장 같은 부수 효과가 생긴다 | 백엔드를 실행하지 않으므로 생기지 않는다 |
| 버튼 클릭이 과금 · 쓰기 · 발송을 일으켜 막아야 했다 | 응답이 가짜이므로 버튼을 눌러 결과 화면까지 캡처한다 |
| 사설 패키지 설치에 토큰 발급이 필요했다 | 백엔드 의존성을 설치하지 않는다 |

화면을 띄우는 방법은 화면 코드의 종류로 정한다.

| 화면 코드 | 띄우는 방법 |
|---|---|
| 정적 HTML · JS(예: email_db 의 `src/web`) | 서버를 띄우지 않는다. `capture.py` 가 가짜 주소의 모든 요청을 가로채, 화면 파일 요청에는 레포의 파일로, API 요청에는 가짜 데이터로 응답한다. 주소와 파일의 대응은 분석이 낸다 |
| Node(`package.json` 의 `dev`, Next.js · Vite) | `run_repo.py` 가 `npm ci`(잠금 파일이 없으면 `npm install --no-save`)로 설치하고 `127.0.0.1` 의 빈 포트로 개발 서버를 띄운다. API 요청은 브라우저 안에서 가로채 가짜 데이터로 응답한다 |

`capture.py` 는 Playwright 의 `channel="chrome"` 으로 PC 에 설치된 Chrome 을 구동하고, 뷰포트는 1440×1000 으로 고정한다. 화면 파일과 가짜 데이터에 없는 요청은 모두 끊는다. 화면 코드가 외부 서비스로 직접 보내는 요청도 나가지 않는다. 버튼은 분석이 지정한 대로 눌러 결과 화면을 `endImg` 로 찍는다.

가짜 데이터는 분석 서브에이전트가 백엔드 코드에서 응답 형태를 읽어 만든다. 가짜 데이터에는 실제 사람 이름 · 회사 메일 주소 · 고객 정보를 쓰지 않고, 「홍길동」 · `user@example.com` 같은 예시 값을 쓴다. 템플릿은 화면 칸 머리에 「예시 데이터로 그린 화면」을 표시한다.

Next.js 처럼 서버가 화면을 미리 채워 보내는 부분은 브라우저 안에서 가로챌 수 없다. 그 부분은 개발 서버가 그린 그대로 찍힌다. 화면 파일을 찾지 못했거나 Node 설치 · 개발 서버 실행이 실패한 기능은 화면 칸에 「화면 코드를 실행하지 못해 화면을 만들 수 없습니다.」를 표시한다. 화면 코드가 없는 레포는 「이 레포에는 화면 코드가 없어 화면을 만들 수 없습니다.」를 표시한다.

스크립트 의존성(Playwright)은 `uv run --no-project --with` 로 설치한다. 사내 SSL 프록시는 PC 에 설정된 `SSL_CERT_FILE` 로 통과한다. 컨트롤 타워 설치기가 윈도우 PC 에 이 값(이 PC 는 `C:\corp-certs\ca-bundle.pem`)을 설정해 두고, 이 값이 없을 때(예: WSL)만 레포의 `certs/ePrism.crt` 로 묶음을 만든다. `run_repo.py exec` 가 이 값을 준 채 명령을 실행한다.

캡처 이미지는 `docs/code-flow/screens/` 에 PNG 로 두고 HTML 이 상대 경로로 읽는다(사용자 결정 2026-10-14). 다른 사람에게 줄 때는 HTML 과 `screens/` 폴더를 함께 줘야 한다.

## 사용자 동작 따라가기

안내 화면은 버튼 클릭만이 아니라 사용자가 실제로 하는 동작(검색어 입력, 목록에서 고르기, 버튼 누르기)을 차례로 따라가며 보여 준다(사용자 결정 2026-10-15, email_db 시험 피드백). 시험 결과물에는 검색 장면에서 검색어를 치는 모습이 없었고, 흐름 그림의 자료 이름도 「검색어 붙인 목록 요청」처럼 일반적인 말이었다. 참고로 삼은 「계산 흐름 검토」 화면(`excel_sample_trace/explain_dramatic.html`)은 `([921.3]-[894.73])/[894.73] = 0.0296961` 처럼 실제 값을 대입해 보여 주어 직관적이었다.

| 바꾸는 것 | 내용 |
|---|---|
| 캡처 동작 | 캡처 계획의 장면에 `steps`(사용자 동작 목록)를 둔다. 동작 종류는 입력 · 누르기 · 고르기 · 기다리기에 우클릭 · 두 번 누르기 · 키 누르기 · 붙여넣기 · 파일 올리기 · 마우스 올리기 · 끌기 · 스크롤을 더한 12가지다(사용자 결정 2026-10-16). 추가한 8가지는 사내 화면 코드 9곳(Kiwoom-Rag, Kiwoom-Agent ESG2 · ESG3 · GM, wholesale-dashboard, excel-dashboard-test, dashboard-template, email_db)에서 찾은 상호작용이다(`onContextMenu` · `onDoubleClick` · `onKeyDown` · `onPaste` · 파일 칸 · `onDrop` · `onMouseEnter` · `onMouseDown` · 스크롤). `capture.py` 는 계획의 동작 칸을 먼저 검사하고, 화면을 새로 연 뒤 동작을 차례로 실행해 결과 화면을 `endImg` 로 찍는다. 멈춘 동작은 결과의 `failed` 에 몇 번째 동작인지와 오류 문구로 남긴다. 첫 동작의 대상 위치가 `screen.start` 가 된다 |
| 가짜 응답의 조건 | 가짜 응답에 `query`(쿼리 조건)를 둘 수 있다. 같은 경로라도 검색어가 든 요청과 처음 목록 요청에 서로 다른 응답을 준다. 조건이 있는 응답을 먼저 맞춘다 |
| 입력 연출 | 장면의 `screen.typed` 에 입력한 글자를 적으면, 템플릿이 검색창으로 줌한 뒤 그 글자를 한 글자씩 쳐 보이고 결과 화면으로 넘어간다 |
| 실제 값 | 흐름 그림의 자료 이름(`text`)과 설명(`say`)에 가짜 데이터의 실제 값을 쓴다. 예: 「"견적" 검색」 → 「제목 · 본문에 "견적"이 든 메일 3통」 |
| 외부 프로그램 열림 | 외부 프로그램과 외부 시스템(아웃룩, 엑셀, WINUS, FAS, 외부 사이트) 노드에 `launch: true` 를 둔다. 장면에서 그 노드가 처음 쓰일 때 템플릿이 아이콘이 창처럼 열리는 동작을 먼저 보여 주고, 그다음 자료가 오간다. 실제 탐색 시간은 생략한다. 레포 자신의 서버와 저장소에는 두지 않는다 |
| 오른쪽 칸 고정 | 오른쪽의 화면 캡처와 「알아 둘 점」은 페이지를 아래로 내려도 화면에 붙어 따라온다. 화면보다 길면 칸 안에서 스크롤한다 |

## 기능 순서와 장면 구성

안내 화면은 기능을 사람이 화면을 보고 실제로 움직이는 순서로 놓는다(사용자 결정 2026-10-16, Kiwoom-RM 시험 피드백). RM 시험 결과물은 분석을 맡긴 순서대로 「위험등급 산정 → 결과 → 코멘트」로 놓였다. 그런데 코멘트 저장이 `WRDSS.DW_T_월간OPERATING_TEST` 에 쓰고(`Kiwoom-RM/src/repositories/comment_repo.py:357`) 등급 정성평가가 같은 테이블을 읽으므로(`src/repositories/risk/loader.py:37-45`, `src/services/risk_grade/qualitative.py:441`) 사람은 코멘트를 먼저 만든다.

주 세션은 아래 기준을 차례로 적용하고, 앞 기준으로 정해지지 않을 때만 다음 기준을 쓴다.

| 기준 | 내용 | 조사에서 순서를 정한 사례 |
|---|---|---|
| 데이터 의존 | 데이터를 쓰는 기능이 그 데이터를 읽는 기능보다 먼저 온다. 사람 사이 순서(한 사람이 올린 자료를 다른 사람이 봄)도 포함한다 | RM 코멘트 → 등급, GM 보유현황 → 하위펀드(탭은 반대), excel 업로드 → 나머지 전부, wholesale 일정 입력 → 홈 D-day |
| 화면이 정한 순서 | 단계 번호, 비활성 조건, 선행 입력 필수 여부를 따른다. 번호 목록이 사용자 동작과 연결될 때만 장면 경계로 쓴다 | ESG3 STEP 1 → STEP 2. wholesale MMF Daily 의 1~7 번호는 스크립트 내부 단계라 쓰지 않음 |
| 시선 순서 | 동작에 차이가 없고, 화면에 순서도 없고, 기능이 서로 독립일 때만 화면의 좌상단에서 오른쪽, 그다음 아래 순서로 놓는다 | excel 의 사이드바 · 알림 · 계정 기능 |

코드 파일 순서, 라우터 등록 순서, JSX 렌더 순서는 근거로 쓰지 않는다. 조사한 레포 여섯 곳(GM, excel-dashboard-test, Kiwoom-Rag ETF, ESG3, wholesale-dashboard, 이메일 · RM, 2026-10-16)에서 모두 사람 순서와 달랐다.

장면 구성은 아래를 따른다.

| 규칙 | 내용 | 근거 |
|---|---|---|
| 수집 과정 먼저 | 크롤링 · 스케줄러처럼 미리 돌아 자료를 모으는 과정은 「수집 과정」 기능으로 맨 앞에 보이고, 뒤의 기능은 그 결과를 쓰는 흐름으로 보인다(사용자 결정 2026-10-16) | 분석은 수집이 끝난 상태를 전제한다 |
| 공통 입력 장면 | 여러 기능이 같이 쓰는 입력(기준 보고월, 대상 선택 방식)은 첫 기능 앞에 장면 하나로 둔다. 다른 기능의 캡처는 이 입력을 `"setup": true` 준비 동작으로 먼저 실행하고, 준비를 마친 화면을 시작 화면(`startImg`)으로 찍는다 | RM 시험에서 기준 보고월이 모든 장면의 준비 동작으로만 들어가 장면이 되지 못했다 |
| 자동 배지 | 사용 중에 사람 동작 없이 일어나는 전환은 흐름 안에 두고 `auto: true` 로 「자동」 배지를 붙인다(사용자 결정 2026-10-16) | ESG3 검증 화면은 평가가 끝나면 0.5초 뒤 자동으로 열린다 |
| 도달 가능한 화면만 | 실제로 렌더되고 화면에서 도달할 수 있는 요소만 장면으로 삼는다. import 사용처와 상태 전이 호출처로 확인한다 | GM 3단계(엑셀 생성), ESG3 「검증 다시 열기」, wholesale `MarketTab` 은 코드만 있고 도달할 수 없다 |
| 선택 입력의 두 경로 | 먼저 고를 수도, 나중에 되물을 때 고를 수도 있는 입력은 주된 경로를 장면으로 보이고 다른 경로는 알아 둘 점 한 줄로 적는다(사용자 결정 2026-10-16) | ETF 바구니 |

## 알아 둘 점

알아 둘 점은 화면만 봐서는 알 수 없는데 모르면 입력이 실패하거나 결과를 잘못 읽는 규칙이다(사용자 결정 2026-10-16). RM 시험 결과물의 「입력 창 아래 "예상 소요시간 3–5분"은 화면에 고정해 둔 안내 문구이며…」처럼 화면 안내를 다시 설명하는 항목은 싣지 않는다. 「펀드코드 칸에 쉼표나 띄어쓰기로 여러 개를 넣으면 묶음 산정으로 바뀐다」 같은 항목이 핵심이다.

| 등급 | 판정 | 예 |
|---|---|---|
| 핵심(`core`) | 화면에 보이지 않고, 모르면 입력이 실패하거나 결과를 잘못 읽는 규칙. 입력 형식, 단위 · 기준 시점, 선행 조건, 결과 해석(값의 출처, 알림 없는 실패), 되돌림 불가, 저장 대상 | 펀드코드 구분자, 임시저장은 WINUS 에 기록하지 않음 |
| 참고(`ref`) | 알면 좋지만 몰라도 틀리지 않는 규칙 | 진행 표시 (n/7)은 4단계를 반복함 |
| 싣지 않음 | 화면에 이미 글자로 보이는 안내를 다시 말하는 항목, 눈에 보이는 상태(테두리, 바탕색)를 묘사만 하는 항목. 그 상태가 무엇을 뜻하는지는 화면에 적혀 있지 않으면 핵심이다 | 「예상 소요시간 3–5분」, 「테두리가 보라색이다」(묘사, 싣지 않음) · 「보라 테두리는 등급이 바뀐 요인이다」(뜻, 핵심) |

판정은 아래 순서로 한다.

- 분석은 화면 문구(placeholder, 안내, 라벨, 빈 상태와 오류 문구)를 먼저 모은 뒤, 그 문구로 이미 보이는 사실을 뺀다. 판정 단위는 문장이 아니라 사실이다. RM 펀드코드 칸 안내는 쉼표 예시만 보이므로(`Kiwoom-Rag/src/frontend/.../InputForm.tsx:246`) 띄어쓰기도 구분자라는 사실은 핵심이다.
- 화면 문구가 실제 동작과 다르면 핵심으로 싣는다. 예: ESG3 의 줄바꿈이 되지 않는 입력창에 적힌 「Shift + Enter로 줄바꿈」, RM 미리보기의 「현재 편집 중인 코멘트는 자동으로 임시저장됩니다」.
- 마우스를 올려야 보이는 툴팁에만 있는 규칙은 핵심 후보로 본다(사용자 결정 2026-10-16). 안내 화면의 캡처에는 툴팁이 찍히지 않는다.
- 분석은 백엔드의 저장 · 조회 코드를 반드시 읽는다. ESG3 핵심 25개 중 18개, excel 업로드 핵심 9개 중 7개가 백엔드에서만 확인되었다.
- 같은 규칙은 처음 나오는 장면에만 싣는다. 이메일 시험 결과물에서 「본문 그림은 첨부가 아님」이 세 장면에 되풀이되었다.
- 개수는 정하지 않는다(사용자 결정 2026-10-16). 조사에서 동작당 핵심은 0개부터 9개까지 나왔고, 핵심이 0개인 동작이 레포마다 16~46% 였다. 장면당 약 5개로 채우던 이전 규칙은 핵심이 없는 장면을 재진술과 참고로 채웠다. 대신 주 세션이 「알아 둘 점 검토」 단계에서 한 번 더 확인한다.

개발자용 안내 화면의 표시는 아래와 같다(사용자 결정 2026-10-16, 결정표 https://claude.ai/artifact/PwMrADLjRt11so1mPPJ7HY). 사용자 설명서는 참고와 결함을 다르게 보인다(「사용자 설명서」 절).

| 대상 | 표시 |
|---|---|
| 핵심 | 17px 문장으로 모두 보인다 |
| 참고 | 「참고 N개 더 보기」로 접어 둔다 |
| 되돌림 불가(`irreversible`) | 핵심 문장 아래에 더 작은 주황 글씨로 「실행 후 되돌아가기 불가」를 붙인다. 접지 않는다 |
| 결함(`defect`) | 빨간 테두리의 「결함」 표시로 싣고, 스킬 실행 끝의 보고에도 `파일:줄` 과 함께 적는다 |
| 기능 사이 선행 조건(`prereq`) | 다음 기능의 첫 장면 위에 주황 띠로 보인다. 예: 「앞 기능에서 코멘트를 위너스 저장해야 등급 산정이 그 코멘트를 읽습니다」 |
| 핵심이 없는 장면 | 알아 둘 점 칸에 참고만 접혀 있거나 칸이 비고, 캡처만 보인다 |

## 화면 항목 목록과 설명 대조

스킬은 화면의 항목을 기능 분석과 따로 나열하고, 모든 항목이 장면이나 알아 둘 점에서 설명되었는지 대조한다(사용자 지적 2026-10-16). 기능 분석은 사람이 하는 동작과 자료 이동에서 출발하므로, 동작 없이 표시로만 뜻을 전하는 항목을 놓친다. RM 시험에서 결과 화면의 보라 테두리 · 「변경」 배지 · 「변경 factor」 버튼은 개발자용 안내 화면의 어느 장면과 알아 둘 점에도 설명되지 않았다. 「변동 펀드」는 PDF · 저장 알아 둘 점에 이름만 나오고 버튼이 하는 일은 설명되지 않았다.

| 단계 | 하는 일 |
|---|---|
| 항목 목록 | 항목 서브에이전트가 화면 하나의 렌더 코드에서 사람이 보는 항목을 모두 나열한다. 나열 대상은 입력 칸, 버튼, 탭, 거르기 버튼, 배지, 색 · 테두리 · 아이콘으로 상태를 보이는 규칙, 툴팁, 빈 상태와 오류 표시다. 조건부로 그려지는 줄 · 조건부 class · 이벤트 처리 줄마다 항목을 내거나 제외 사유를 적는다. 반복해서 그려지는 카드 · 행은 종류마다 한 항목으로 센다. 도달할 수 없는 항목은 뺀다(「기능 순서와 장면 구성」의 도달 가능한 화면 규칙) |
| 뜻 찾기 | 항목 서브에이전트가 항목마다 값의 출처를 코드에서 거꾸로 따라가 뜻을 적고 근거 `파일:줄` 을 단다(「설명서의 0번 화면 둘러보기」 절의 방법). 항목은 렌더 줄을 근거로 늘 내고, 뜻은 닿은 데까지만 적는다. 추적은 테이블 · 외부 응답 · LLM 출력에 닿으면 멈춘다. 뜻을 정하지 못한 항목은 주 세션이 보고에 남긴다 |
| 대조 | 주 세션이 항목마다 설명된 곳을 찾는다. 사람이 누르거나 고르는 항목은 장면에서, 표시 규칙은 알아 둘 점에서 설명되어야 한다 |
| 채우기 | 장면이 없는 버튼이 있으면, 주 세션이 그 기능의 분석 서브에이전트를 빠진 버튼 목록과 함께 다시 실행해 장면을 받는다(사용자 결정 2026-10-16). 추가 장면도 근거 대조 · 알아 둘 점 검토 · 캡처를 거친다. 모르면 결과를 잘못 읽는 표시 규칙이 알아 둘 점에 없으면, 주 세션이 그 화면이 처음 나오는 장면의 알아 둘 점에 핵심으로 싣는다(사용자 결정 2026-10-16). 이렇게 넣은 핵심도 「알아 둘 점 검토」의 기준으로 확인한다 |

장면과 알아 둘 점은 개발자용 안내 화면과 사용자 설명서가 같은 `flow.json` 에서 그린다. 그래서 대조로 채운 장면과 알아 둘 점은 두 결과물에 함께 나타난다. 화면 둘러보기는 사용자 설명서에만 있으므로 대조에서 설명된 곳으로 세지 않는다. 대조 결과는 답에만 적고 파일로 남기지 않는다(사용자 결정 2026-10-16, 렌더와 다른 단계가 읽지 않고 다시 실행하면 덮어쓰이기 때문이다).

## 챗봇 기능 (개발 중)

챗봇처럼 대화 입력과 도구 호출(tool calling)로 진행되는 기능은 일반 화면과 다른 규칙을 따로 만든다(사용자 결정 2026-10-16). 규칙은 아직 정하지 않았다. 지금 스킬은 그런 기능을 만나면 장면을 만들지 않고, 안내 화면의 기능 칸과 보고에 「챗봇 기능 안내는 개발 중입니다」를 적는다.

이 결정 전에 조사한 내용을 규칙을 만들 때의 참고로 남긴다(2026-10-16, Kiwoom-Rag 브랜치 `feat/basket-phase2-excel` `109d6b3b` 의 ETF 화면, Kiwoom-Agent/GM 채팅).

| 항목 | 관찰 |
|---|---|
| 순서 · 핵심 판정 | ETF 도 데이터 의존(펀드 → 종목 · BM, 개요 → 상품특징)과 화면 순서(하위 명령 순서)가 들어맞았다. 핵심도 같은 유형이었다(미래 날짜를 최신 영업일로 보정, 모든 칸이 차면 바로 실행, 첨부 시 자동 버전 저장) |
| 장면 단위 | 대화 한 번이 입력 → (되묻기 패널) → 답변이다. 같은 명령에도 답이 바로 오는 흐름과 되묻는 흐름이 나뉜다 |
| 사용자 입력 | 자연어라서 어떤 표현을 알아듣는지가 핵심이 된다 |
| 가짜 응답 | 스트리밍 응답(SSE)과, 답변 속 표시가 바구니 · 패널을 여는 동작을 재현해야 한다. Playwright 로 SSE 본문을 한 번에 돌려주면 최종 화면은 그려진다고 가정하며 확인하지 않았다 |
| 두 경로 | 바구니처럼 선택 사항인 입력이 명령 앞과 되묻기 단계에 모두 나타난다 |
| GM 채팅 | 화면은 있으나 GM 백엔드에 `/chat/stream` 라우트가 없다(`Kiwoom-Agent/GM/src/frontend/src/setupProxy.js:7`, 백엔드 `app.py:111-125`) |

## 사용자 설명서

스킬은 개발자용 안내 화면과 함께 사용자 설명서를 만든다(사용자 결정 2026-10-16). 사용자 설명서는 화면을 쓰는 사람이 읽는다. 설명서는 개발 내부(서버, 함수, 저장 방식)를 빼고, 화면의 각 항목과 버튼의 뜻과 데이터 출처(WINUS · FAS · 외부 서비스)를 보인다. 시안은 https://claude.ai/artifact/XMKjr2vfuNaCMw5CRkx3kb 에 있다.

스킬은 `index.html` 과 `manual.html` 을 언제나 함께 만들고, 같은 `flow.json` 에서 그린다(사용자 결정 2026-10-16). 설명서만 만드는 선택지나 설명서용으로 줄인 분석은 두지 않는다. 기능 순서의 첫 기준인 데이터 의존과 핵심 알아 둘 점의 대부분은 백엔드 저장 · 조회 코드를 읽어야 확인된다(ESG3 핵심 25개 중 18개, excel 업로드 핵심 9개 중 7개, 「알아 둘 점」 절). 같은 `flow.json` 을 쓰면 두 HTML 의 기능 순서 · 장면 · 알아 둘 점 · 선행 조건 띠가 항상 같다.

| 화면 요소 | 설명서의 처리 |
|---|---|
| 캡처 | 가운데에 크게 두고, 개발자용 안내 화면과 같은 줌 · 입력 연출 · 화면 겹쳐 바꾸기로 움직인다 |
| 흐름 그림 · 동작 설명(`actions`) | 그리지 않는다. 데이터 의존과 데이터 출처를 동작에서 뽑으므로 분석은 그대로 만든다 |
| 이 기능으로 하는 일 | 오른쪽 칸 맨 위에 가장 크게 보인다. 기능 `summary` 를 쓴다 |
| 데이터 출처 | 구역이 `winus` · `fund` · `external` 인 노드 이름을 뽑아 「이 기능으로 하는 일」 아래 한 줄로 보인다 |
| 알아 둘 점 | 「이 기능으로 하는 일」보다 작은 글자와 옅은 테두리로 보인다. 참고는 접지 않고 핵심 아래 「참고」 제목과 작은 회색 글씨로 모두 보인다(사용자 결정 2026-10-16. 설명서 독자가 접힌 내용을 열지 않을 것이라는 사용자 판단이다). 되돌림 불가 주황 표시는 개발자용 안내 화면과 같다 |
| 결함(`defect`) | 숨긴다(사용자 결정 2026-10-16). 사용자 행동에 영향을 주는 결함은 「화면과 문장 규칙」대로 핵심 알아 둘 점으로 따로 적는다. 예: 「완료 알림이 떠도 저장이 실패했을 수 있습니다」 |
| 선행 조건 띠 · 자동 배지 | 개발자용 안내 화면과 같이 보인다 |
| 재생 막대 | 화면 아래에 고정하고, 전체 재생 · 이전 · 다음 장면 · 다시 보기 · 재생 속도를 둔다. 재생 속도 범위 0.5~2배는 개발자용 템플릿과 같은 값이다 |
| 배율과 글자 크기 | 개발자용 템플릿과 같은 배율 식(창 폭 ÷ 2400, 0.6~1배)과 글자 크기를 쓴다 |
| 오른쪽 칸 위치 | 장면 제목 아래에서 캡처 칸과 같은 높이로 시작한다 |
| 칸 폭 | 캡처 칸과 오른쪽 칸 사이에 구분선을 둔다. 사용자가 구분선을 끌면 폭 비율(30~80%)이 바뀌고, 브라우저가 고른 비율을 기억한다. 범위와 기본 비율 3 : 2 는 개발자용 템플릿과 같은 값이다 |
| 시작 줌 | 개발자용 안내 화면과 같은 `capture.py` 결과를 쓴다. 그래서 앞쪽에 이어진 입력 · 고르기 칸(연도 → 월)을 함께 감싼 사각형으로 줌한다 |

## 설명서의 0번 화면 둘러보기

사용자 설명서는 맨 위에 「0. 화면 둘러보기」 묶음을 하나 두고, 기능은 1번부터 센다(사용자 결정 2026-10-16). 같은 화면을 여러 기능이 쓰므로 둘러보기를 기능마다 붙이지 않는다. 개발자용 안내 화면에는 넣지 않는다(사용자 결정 2026-10-16). 개발자용 안내 화면은 흐름 그림 무대가 화면 칸을 차지해 번호가 작게 보이기 때문이다.

주 세션은 둘러보기에 넣을 화면을 장면 캡처의 서로 다른 결과 화면(`endImg`)에서 고른다. RM 에서는 입력 창, 코멘트 생성 결과 창, 위험등급 산정 결과 화면이다. 둘러보기 화면에 닿는 동작과 가짜 데이터는 그 장면의 것을 재사용한다. 주 세션은 설명 대조 단계에서 표시 규칙(예: 보라 테두리)이 그 캡처의 가짜 데이터로 실제로 그려졌는지도 확인한다.

둘러보기 화면은 움직이지 않는다(사용자 결정 2026-10-16). `manual_template.html` 은 화면 전체에 번호를 찍고, 사용자가 오른쪽 「화면 항목」 표의 줄에 마우스를 올리면 그 칸에 테두리를 그린다. 전체 재생 중에는 템플릿이 둘러보기 화면을 6초 보여 준 뒤 다음 장면으로 넘어간다. 6초는 시안의 값이다.

| 단계 | 하는 일 |
|---|---|
| 항목 서브에이전트 | 「화면 항목 목록과 설명 대조」 절의 항목 서브에이전트가 `areas-prompt.md` 에 따라 화면마다 `areas` 를 낸다. 기능 분석 서브에이전트는 `areas` 를 내지 않는다. 이름 있는 칸, 표시로만 뜻을 전하는 항목(RM 결과 화면의 보라 테두리와 「변경」 배지), 거르기 버튼(「변경 factor」, 「변동 펀드」)을 모두 항목으로 낸다. 시안에서 칸 이름만 골랐을 때 이 표시가 빠졌다. 항목마다 이름, 뜻, 찾는 방법(`target`), 근거 `파일:줄` 을 적는다. 뜻은 화면 칸에서 출발해 값의 출처를 코드에서 거꾸로 따라가(화면 상태 → API 응답 필드 → 백엔드 계산 · 조회 → 테이블) 닿은 데까지만 적는다. 업무 용어의 뜻(예: 공실률, DSCR)은 레포의 프롬프트 · 문서에 정의가 있을 때만 적는다 |
| 캡처 | `capture.py` 가 둘러보기 화면에서 항목마다 위치를 측정한다. 화면에 보이는 후보가 없거나 둘 이상이면 「찾지 못함」으로 처리하고, 주 세션은 그 항목을 번호 없이 표에만 남긴다. 행마다 그려지는 표시 규칙은 첫 번째 해당 요소를 대상으로 삼는다 |
| 검사 | `render.py` 가 위치 범위와 번호 중복을 검사한다. 번호 표시끼리 겹치면 렌더를 멈추지 않고, 템플릿이 뒤 번호를 비켜 놓는다. 배지가 테두리 안에 있는 것처럼 사각형끼리 포함되는 것은 겹침으로 보지 않는다 |
| 템플릿 | `manual_template.html` 이 번호 표시와 「화면 항목」 표를 그린다 |

주 세션은 이 방법으로 RM 결과 화면의 항목 뜻을 뽑아 보았다(2026-10-16, 백엔드 Kiwoom-RM main `306a76f2`, 화면 코드 Kiwoom-Rag `feat/basket-phase2-excel` `109d6b3b`). 주 세션은 시안에 처음에 「이전」 배지를 「지난달 WINUS 에 저장된 등급」으로 추정해 적었다. 그런데 조회 코드는 직전 월에 기록이 없으면 더 앞선 달까지 내려갔다. 그래서 항목 서브에이전트는 근거 없는 뜻을 싣지 않는다.

| 항목 | 따라간 경로 | 뽑은 뜻 |
|---|---|---|
| Operating Info 원본 | `ReasoningSection.tsx:79-85` → `RiskGradeResultView.tsx:465` → `evaluator.py:855` → `qualitative.py:441` → `loader.py:37-45`(`DW_T_월간OPERATING_TEST`) | 등급을 매길 때 읽은 이번 보고월의 운용 코멘트 원문입니다. WINUS 에 저장한 코멘트만 나오고, 없으면 「Operating Info가 없습니다」가 보입니다 |
| 펀드 종합등급의 「이전」 | `GradeSummary.tsx:36-39` → `RiskGradeResultView.tsx:351` → `useRiskGrade.ts:68-80` → `grades.py:365` → `loader.py:252-272`(`DW_T_월간RISKCHECK_TEST`) | 직전 월까지 WINUS 에 저장된 가장 최근 위험등급입니다. 직전 월에 기록이 없으면 그보다 앞선 달의 등급을 보입니다. 알아 둘 점 후보: 기록이 없으면 G 로 보입니다. 이력 조회에 실패하면 일반 펀드는 G 로, 블라인드 펀드는 현재 종합등급과 같은 등급으로 보입니다(`useRiskGrade.ts:80`) |

## 설명서와 원본 관리

스크립트와 지침은 한 벌만 둔다(사용자 결정 2026-10-16). `render.py` 가 `flow.json` 하나로 `index.html` 과 `manual.html` 을 함께 만들고, `movie_template.html` 과 `manual_template.html` 은 `scripts/` 에 나란히 둔다.

## 결과물 위치

결과물은 분석 대상 레포의 `docs/code-flow/` 폴더에 만들고, 폴더 전체를 git 에서 제외한다(사용자 결정 2026-10-14). 캡처 이미지와 HTML 안의 JSON 에는 화면에 뜬 실제 데이터(고객명 · AUM · 담당자 정보)가 들어가고, 커밋하면 지워도 git 이력에 남기 때문이다.

| 파일 | 내용 |
|---|---|
| `docs/code-flow/index.html` | 개발자용 안내 화면 |
| `docs/code-flow/manual.html` | 사용자 설명서 |
| `docs/code-flow/screens/*.png` | 캡처 이미지 |
| `docs/code-flow/flow.json` | 문구만 고쳐 다시 렌더할 때 쓰는 합친 JSON |
| `docs/code-flow/.gitignore` | 내용이 `*` 한 줄인 제외 파일 |

스킬은 레포 루트 `.gitignore` 를 고치지 않는다. `docs/code-flow/.gitignore` 는 자기 자신을 포함한 폴더 전체를 제외하므로 git 변경을 만들지 않는다. `uv` 가 `.venv` 를 만들 때도 같은 방식을 쓴다(uv 0.11.5 로 만든 `Kiwoom-ETF/.venv/.gitignore` 의 내용이 `*` 다). 다시 실행하면 폴더 내용을 덮어쓴다. 스킬은 결과를 만든 뒤 `git status --short docs/code-flow` 가 빈 출력인지 확인한다.

## 제외 범위

아래 작업은 이 스킬이 하지 않는다.

- 레포 코드를 고치지 않고, 불일치는 보고만 한다.
- 주 세션은 애니메이션 재생을 헤드리스로 검증하지 않고, 재생은 사용자가 브라우저에서 확인한다.
- 시제품의 단계 화면(`flow_template.html`)은 만들지 않는다.
- 화면 코드가 다른 레포에 있는 레포는 지원하지 않는다(사용자 결정 2026-10-16). 예를 들어 Kiwoom-RM 의 화면은 Kiwoom-Rag 에 있다. RM 시험에서는 주 세션이 손으로 맞췄다. 분석 프롬프트에 두 레포 경로를 넣었고, Kiwoom-Rag 에서 개발 서버를 띄웠으며, 로그인 확인 요청에 가짜 응답을 주고 「리스크 관리」 클릭을 준비 동작으로 넣었다.

애니메이션을 헤드리스로 검증하지 않는 이유는 시제품 작업 중 관찰에 있다. `--virtual-time-budget` 을 준 헤드리스 Chrome 캡처에서 Web Animations 와 CSS 전환이 진행되지 않았다. 그래서 주 세션은 정지 상태만 캡처해 확인한다.
